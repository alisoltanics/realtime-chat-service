# چت بلادرنگ

این مخزن یک نمونهٔ چت متنی است که پیام‌ها را بدون تازه‌کردن صفحه به کاربران می‌رساند. برنامه از سه بخش تشکیل شده: API با Django و DRF، سرویس WebSocket با Node.js و Socket.IO، و رابط کاربری React. PostgreSQL پیام‌ها را نگه می‌دارد؛ وضعیت آنلاین فعلاً فقط در حافظهٔ سرویس realtime است.

جریان پیام ساده است: مرورگر پیام را به سرویس realtime می‌فرستد، سرویس آن را برای ذخیره به Django می‌دهد و بعد از ذخیرهٔ موفق، پیام را برای اعضای اتاق پخش می‌کند.

API در مسیر `/api/v1/` نسخه‌بندی شده است. مسیرهای قدیمی `/api/` فعلاً برای سازگاری در دسترس‌اند؛ مسیرها و payloadها در [قرارداد API](docs/API_CONTRACT.md) آمده‌اند.

```
┌──────────────┐   REST (JWT)   ┌──────────────┐   ORM    ┌────────────┐
│   frontend   │───────────────▶│  django-api  │─────────▶│ postgres   │
│ React + MUI  │                │  DRF + JWT   │          │            │
│              │◀───────────────▶│              │◀─────────│            │
└──────────────┘  Socket.IO      └──────▲───────┘          └────────────┘
                 (WebSocket)           │ internal API
┌──────────────┐                        │
│   realtime   │────────────────────────┘
│ Node + Socket │
└──────────────┘
```

## اجرا

از فایل نمونه، تنظیمات محلی را بسازید:

```bash
cp .env.example .env
```

در `.env` مقدارهای `DJANGO_SECRET_KEY` و `INTERNAL_SERVICE_TOKEN` را عوض کنید، بعد سرویس‌ها را بالا بیاورید:

```bash
docker compose up -d --build
```

دادهٔ نمونه لازم نیست، اما برای ورود سریع می‌توانید کاربران و پیام‌های آزمایشی بسازید:

```bash
docker compose exec django-api python manage.py seed_demo --messages 80
```

سرویس‌ها به‌طور پیش‌فرض روی این نشانی‌ها در دسترس‌اند:

| سرویس | نشانی | متغیر پورت |
|---|---|---|
| رابط کاربری | http://localhost:5173 | `FRONTEND_PORT` |
| API جنگو | http://localhost:8000 | `DJANGO_API_PORT` |
| realtime | http://localhost:4000 | `REALTIME_PORT` |
| PostgreSQL | `localhost:5433` | `POSTGRES_PORT_HOST` |

دادهٔ نمونه شامل دو حساب `ali / ali12345` و `sara / sara12345` است. برای امتحان چت، برنامه را در دو مرورگر باز کنید، با هر حساب وارد شوید و به اتاق «عمومی» بروید. پیام باید در مرورگر دیگر بی‌درنگ دیده شود؛ شمارندهٔ کاربران آنلاین هم با ورود یا بستن تب تغییر می‌کند.

## تست‌ها

```bash
# تست‌های Django
docker compose exec -T django-api python manage.py test chat -v 2

# تست‌های سرویس realtime
docker compose exec -T realtime npm test

# تست سرتاسری دو کاربره
docker compose --profile test run --rm smoke
```

تست سرتاسری به کاربران نمونه نیاز دارد؛ پیش از اجرای آن، دستور `seed_demo` را اجرا کنید. تست ورود، رد اتصال بدون توکن، عضویت در اتاق، وضعیت آنلاین، تحویل پیام، جلوگیری از پیام تکراری، صفحه‌بندی تاریخچه، دسترسی ادمین به اتاق خصوصی و پاک‌شدن وضعیت آنلاین پس از قطع اتصال را بررسی می‌کند.

## چند نکته دربارهٔ پیاده‌سازی

- Django مرجع اصلی داده و هویت کاربر است. سرویس Node.js اتصال‌های WebSocket را مدیریت می‌کند.
- پیام قبل از پخش در PostgreSQL ذخیره می‌شود؛ در نتیجه کلاینت پیام تأییدنشده‌ای دریافت نمی‌کند.
- هویت فرستنده از توکن کاربر به دست می‌آید. سرور مقدار `sender` ارسالی از مرورگر را قبول نمی‌کند.
- `client_id` و قید یکتای `(room, sender, client_id)` جلوی ذخیرهٔ دوبارهٔ یک پیام را می‌گیرند. رابط کاربری هم پیام‌ها را با `message.id` یکی می‌کند.
- تاریخچه با `before_id` صفحه‌بندی می‌شود تا هنگام رسیدن پیام‌های تازه، جای پیام‌های قدیمی در صفحه جابه‌جا نشود.
- وضعیت آنلاین در حافظهٔ یک نمونه از سرویس نگهداری می‌شود. اگر چند نمونه اجرا کنید، این وضعیت بین آن‌ها مشترک نخواهد بود؛ برای آن حالت باید از Redis استفاده شود.

جزئیات قرارداد درخواست‌ها و رویدادها در [قرارداد API](docs/API_CONTRACT.md) است. دلیل انتخاب‌های معماری و محدودیت‌هایشان را هم در [تصمیم‌های معماری](docs/DECISIONS.md) نوشته‌ایم.

## تنظیمات مهم

فهرست کامل تنظیمات در `.env.example` است. این‌ها مهم‌ترین مواردند:

| متغیر | پیش‌فرض | کاربرد |
|---|---|---|
| `DJANGO_SECRET_KEY` | — | کلید محرمانهٔ Django؛ برای هر محیط مقدار جداگانه بگذارید. |
| `INTERNAL_SERVICE_TOKEN` | — | احراز هویت درخواست‌های داخلی بین Django و realtime |
| `CORS_ALLOWED_ORIGINS` | — | مبدأهایی که اجازهٔ دسترسی به API دارند |
| `MAX_MESSAGE_LENGTH` | `4000` | حداکثر طول پیام |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_MESSAGES` | `10000` / `20` | بازه و تعداد مجاز پیام‌ها برای هر اتصال |
| `PRESENCE_TTL_MS` | `90000` | مهلت حضور پس از آخرین heartbeat |
| `PRESENCE_SWEEP_INTERVAL_MS` | `15000` | فاصلهٔ پاک‌سازی اتصال‌های منقضی‌شده |
| `HEARTBEAT_INTERVAL_MS` | `25000` | فاصلهٔ ارسال heartbeat |

`PRESENCE_TTL_MS` را بزرگ‌تر از `HEARTBEAT_INTERVAL_MS` نگه دارید؛ وگرنه ممکن است اتصال سالم پیش از heartbeat بعدی منقضی شود.

## سلامت و گزارش‌ها

- `GET /healthz` سلامت سرویس را گزارش می‌کند. health check سرویس realtime دسترسی به Django را هم می‌سنجد و در صورت مشکل، پاسخ `503` می‌دهد.
- `GET /readyz` وضعیت آماده‌به‌کار بودن را نشان می‌دهد و `GET /presence?room=<slug>` وضعیت آنلاین یک اتاق را برمی‌گرداند.
- گزارش‌ها به‌شکل JSON و یک خطی هستند و `request_id` دارند. متن پیام و توکن‌ها در گزارش ثبت نمی‌شوند؛ فقط طول متن پیام ثبت می‌شود.

## محدودیت‌های فعلی

- وضعیت آنلاین فقط در همان نمونهٔ realtime نگهداری می‌شود؛ برای اجرای چند نمونه باید آن را به Redis منتقل کرد.
- ویرایش و حذف پیام، پیوست و اعلان push هنوز پیاده‌سازی نشده‌اند.
- عضو اتاق خصوصی را می‌توان با `POST /api/v1/rooms/<slug>/members/` اضافه کرد؛ در رابط کاربری هنوز گزینهٔ دعوت وجود ندارد.
- توکن دسترسی در `localStorage` نگهداری می‌شود. برای انتشار عمومی، بهتر است احراز هویت به کوکی `httpOnly` یا روش چرخشی refresh token منتقل شود.
