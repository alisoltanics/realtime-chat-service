# چت متنی بلادرنگ (نسخهٔ اولیه)

این پروژه یک برنامهٔ چت متنی بلادرنگ است که از سه سرویس جداگانه تشکیل شده است: API مبتنی بر Django، سرویس ارتباط بلادرنگ با Node.js و رابط کاربری React. پیام‌ها در PostgreSQL ذخیره می‌شوند و وضعیت آنلاین کاربران در حافظهٔ سرویس realtime نگهداری می‌شود. در این نسخه از Redis، Kafka یا Django Channels استفاده نشده است.

```
┌──────────────┐   REST (JWT)   ┌──────────────┐   ORM    ┌────────────┐
│   frontend   │───────────────▶│  django-api  │─────────▶│ postgres   │
│ React + MUI  │                │  DRF + JWT   │          │            │
│              │◀───────────────▶│              │◀─────────│            │
└──────────────┘  Socket.IO      └──────▲───────┘          └────────────┘
                 (WebSocket)           │ internal API
┌──────────────┐                        │
│   realtime   │────────────────────────┘
│ Node + Socket │
└──────────────┘
```

## راه‌اندازی

```bash
cp .env.example .env
```

فایل `.env` را باز کنید و مقدارهای `DJANGO_SECRET_KEY` و `INTERNAL_SERVICE_TOKEN` را تغییر دهید. سپس سرویس‌ها را اجرا کنید:

```bash
docker compose up -d --build
```

برای ساخت داده‌های نمونه (اختیاری):

```bash
docker compose exec django-api python manage.py seed_demo --messages 80
```

| سرویس | نشانی پیش‌فرض | متغیر تغییر پورت |
|---|---|---|
| رابط کاربری | http://localhost:5173 | `FRONTEND_PORT` |
| API جنگو | http://localhost:8000 | `DJANGO_API_PORT` |
| سرویس بلادرنگ | http://localhost:4000 | `REALTIME_PORT` |
| PostgreSQL | `localhost:5433` | `POSTGRES_PORT_HOST` |

دستور `seed_demo` دو کاربر نمونه می‌سازد: `ali / ali12345` و `sara / sara12345`.

برای بررسی دستی، برنامه را در دو مرورگر جدا باز کنید. با هر مرورگر وارد یکی از حساب‌های نمونه شوید و به اتاق «عمومی» بروید. پیام‌ها بدون بارگذاری دوبارهٔ صفحه نمایش داده می‌شوند. شمارندهٔ کاربران آنلاین بین دو مرورگر به‌روز می‌شود و با بستن یکی از تب‌ها تغییر می‌کند.

## اجرای تست‌ها

```bash
# تست‌های Django، روی پایگاه دادهٔ تست داخل کانتینر
docker compose exec -T django-api python manage.py test chat -v 2

# تست‌های سرویس realtime
docker compose exec -T realtime npm test

# تست سرتاسری با دو کاربر روی سرویس‌های در حال اجرا
docker compose --profile test run --rm smoke
```

برای اجرای تست سرتاسری، ابتدا کاربران نمونه را با دستور `seed_demo` بسازید. این تست هشت مورد را بررسی می‌کند: ورود، رد اتصال بدون توکن، پیوستن به اتاق و ثبت وضعیت آنلاین، دریافت زندهٔ پیام، جلوگیری از ثبت تکراری پیام، صفحه‌بندی تاریخچه، عضویت ادمین در اتاق خصوصی و پاک شدن وضعیت آنلاین پس از قطع اتصال.

## ساختار پروژه

```

  chat/views.py     APIهای عمومی و داخلی
  chat/tests/       ۳۵ تست

  src/socketHandlers.js   احراز هویت اتاق و پخش پیام
  src/presence.js         نگهداری وضعیت آنلاین در حافظه با TTL
  src/heartbeat.js        تازه‌کردن مهلت حضور
```

## تصمیم‌های معماری

- **ارتباط WebSocket در سرویس Node.js است:** Django فقط درخواست‌های HTTP را پردازش می‌کند و مرجع اصلی داده‌هاست.
- **پیام پیش از پخش ذخیره می‌شود:** سرویس realtime پیام را از طریق API داخلی به Django می‌فرستد. پس از ذخیره، همان پیام ذخیره‌شده را برای کاربران پخش می‌کند.
- **فرستنده را سرور تعیین می‌کند:** سرور مقدار `sender` ارسالی از مرورگر را نمی‌پذیرد. سرویس realtime کاربر را با JWT شناسایی می‌کند و پیام را با هویت تأییدشده ذخیره می‌کند.
- **ارسال تکراری پیام کنترل می‌شود:** هر پیام یک `client_id` دارد. قید یکتای `(room, sender, client_id)` مانع ثبت دوبارهٔ همان پیام می‌شود؛ رابط کاربری نیز با `message.id` از نمایش تکراری جلوگیری می‌کند.
- **تاریخچه با صفحه‌بندی کلیدی دریافت می‌شود:** به‌جای `OFFSET` از `before_id` استفاده می‌شود تا با بزرگ‌شدن جدول، جای پیام‌ها در صفحه‌ها جابه‌جا نشود.
- **وضعیت آنلاین در حافظه نگهداری می‌شود:** هر پردازه از `Map`، مهلت انقضا (TTL) و پاک‌سازی دوره‌ای استفاده می‌کند. برای اجرای چند نمونه از سرویس، این بخش باید به Redis منتقل شود.

شرح کامل‌تر تصمیم‌ها و بده‌بستان‌های معماری در فایل [`docs/DECISIONS.md`](docs/DECISIONS.md) آمده است.

## تنظیمات

تنظیمات سرویس‌ها از متغیرهای محیطی خوانده می‌شوند. فهرست کامل را در `.env.example` ببینید.

| متغیر | مقدار پیش‌فرض | کاربرد |
|---|---|---|
| `DJANGO_SECRET_KEY` | — | کلید محرمانهٔ Django؛ برای هر محیط باید مقدار امن و جداگانه داشته باشد. |
| `INTERNAL_SERVICE_TOKEN` | — | توکن مشترک برای ارتباط داخلی Django و سرویس realtime |
| `CORS_ALLOWED_ORIGINS` | — | نشانی‌های مجاز برای دسترسی رابط کاربری |
| `MAX_MESSAGE_LENGTH` | `4000` | بیشترین طول پیام |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_MESSAGES` | `10000` / `20` | بازه و حداکثر تعداد پیام مجاز برای هر اتصال |
| `PRESENCE_TTL_MS` | `90000` | مدت اعتبار وضعیت آنلاین، بدون دریافت heartbeat |
| `PRESENCE_SWEEP_INTERVAL_MS` | `15000` | فاصلهٔ زمانی پاک‌سازی وضعیت‌های منقضی‌شده |
| `HEARTBEAT_INTERVAL_MS` | `25000` | فاصلهٔ زمانی ارسال heartbeat برای تازه‌کردن مهلت حضور |

مقدار `PRESENCE_TTL_MS` باید به‌مراتب بیشتر از `HEARTBEAT_INTERVAL_MS` باشد تا اتصال‌های سالم پیش از دریافت heartbeat بعدی منقضی نشوند.

## سلامت سرویس و گزارش‌ها

- مسیر `GET /healthz` وضعیت سلامت سرویس را برمی‌گرداند. سرویس realtime دسترسی به Django را هم بررسی می‌کند و اگر Django در دسترس نباشد، پاسخ `503` می‌دهد.
- مسیرهای `GET /readyz` و `GET /presence?room=<slug>` برای بررسی آماده‌به‌کار بودن سرویس و مشاهدهٔ وضعیت آنلاین اتاق هستند.
- هر سرویس گزارش‌ها را به‌شکل JSON و در یک خط ثبت می‌کند. گزارش‌ها شامل `request_id` هستند؛ متن پیام و توکن‌ها ثبت نمی‌شوند و فقط طول متن پیام گزارش می‌شود.

## محدودیت‌های فعلی

- وضعیت آنلاین فقط در حافظهٔ یک نمونه از سرویس نگهداری می‌شود. برای اجرای چند نمونه، باید از Redis استفاده شود.
- ویرایش یا حذف پیام، پیوست و اعلان فوری (push) در این نسخه وجود ندارد.
- افزودن عضو به اتاق خصوصی فقط از طریق API با درخواست `POST /api/rooms/<slug>/members/` ممکن است؛ رابط کاربری دکمهٔ دعوت ندارد.
- توکن دسترسی در `localStorage` مرورگر ذخیره می‌شود. برای انتشار عمومی، بهتر است روش امن‌تری مانند کوکی `httpOnly` یا سازوکار چرخشی refresh token به‌کار گرفته شود.
