# Real-Time Chat

این مخزن یک نمونهٔ چت متنی است که پیام‌ها را بدون تازه‌کردن صفحه به کاربران می‌رساند. برنامه از سه بخش تشکیل شده: API با Django و DRF، سرویس WebSocket با Node.js و Socket.IO، و رابط کاربری React. PostgreSQL پیام‌ها را نگه می‌دارد؛ وضعیت آنلاین فعلاً فقط در حافظهٔ سرویس realtime است.

جریان پیام ساده است: مرورگر پیام را به سرویس realtime می‌فرستد، سرویس آن را برای ذخیره به Django می‌دهد و بعد از ذخیرهٔ موفق، پیام را برای اعضای اتاق پخش می‌کند.


```
┌──────────────┐   REST (JWT)   ┌──────────────┐   ORM    ┌────────────┐
│   frontend   │───────────────▶│  django-api  │─────────▶│ postgres   │
│ React + MUI  │                │  DRF + JWT   │          │            │
│              │◀───────────────▶│              │◀─────────│            │
└──────────────┘  Socket.IO      └──────▲───────┘          └────────────┘
                 (WebSocket)           │ internal API
┌──────────────┐                        │
│   realtime   │────────────────────────┘
│ Node + Socket │
└──────────────┘
```

## اجرا

از فایل نمونه، تنظیمات محلی را بسازید:

```bash
cp .env.example .env
```

در `.env` مقدارهای `DJANGO_SECRET_KEY` و `INTERNAL_SERVICE_TOKEN` را عوض کنید، بعد سرویس‌ها را بالا بیاورید:

```bash
docker compose up -d --build
```

فرانت‌اند در Compose با Vite اجرا می‌شود؛ تغییر فایل‌های `frontend/src` خودکار در مرورگر دیده می‌شود و برای تغییرات معمول رابط کاربری نیازی به build دوباره نیست. فقط بعد از تغییر وابستگی‌های npm، سرویس فرانت را یک‌بار با `docker compose up -d --build frontend` بازسازی کنید.

دادهٔ نمونه لازم نیست، اما برای ورود سریع می‌توانید کاربران و پیام‌های آزمایشی بسازید:

```bash
docker compose exec django-api python manage.py seed_demo --messages 80
```

سرویس‌ها به‌طور پیش‌فرض روی این نشانی‌ها در دسترس‌اند:

| سرویس | نشانی | متغیر پورت |
|---|---|---|
| رابط کاربری | http://localhost:5173 | `FRONTEND_PORT` |
| API جنگو | http://localhost:8000 | `DJANGO_API_PORT` |
| realtime | http://localhost:4000 | `REALTIME_PORT` |
| PostgreSQL | `localhost:5433` | `POSTGRES_PORT_HOST` |

دادهٔ نمونه شامل دو حساب `ali / ali12345` و `sara / sara12345` است. برای امتحان چت، برنامه را در دو مرورگر باز کنید، با هر حساب وارد شوید و به اتاق «عمومی» بروید. پیام باید در مرورگر دیگر بی‌درنگ دیده شود؛ شمارندهٔ کاربران آنلاین هم با ورود یا بستن تب تغییر می‌کند.

## تست‌ها

```bash
# تست‌های Django
docker compose exec -T django-api python manage.py test chat -v 2

# تست‌های سرویس realtime
docker compose exec -T realtime npm test

# تست سرتاسری دو کاربره
docker compose --profile test run --rm smoke
```

تست سرتاسری به کاربران نمونه نیاز دارد؛ پیش از اجرای آن، دستور `seed_demo` را اجرا کنید. تست ورود، رد اتصال بدون توکن، عضویت در اتاق، وضعیت آنلاین، تحویل پیام، جلوگیری از پیام تکراری، صفحه‌بندی تاریخچه، دسترسی ادمین به اتاق خصوصی و پاک‌شدن وضعیت آنلاین پس از قطع اتصال را بررسی می‌کند.

## مدل‌های پایگاه داده

داده‌های پایدار در PostgreSQL و با ORM جنگو نگهداری می‌شوند. مدل کاربر همان `django.contrib.auth.User` است؛ مدل سفارشی کاربر نداریم.

<ul dir="rtl">
  <li><code>User</code>: حساب کاربر را نگه می‌دارد. نام کاربری یکتا است و گذرواژه به‌شکل hash ذخیره می‌شود.</li>
  <li><code>Room</code>: نام، شناسهٔ یکتای نشانی (<code>slug</code>)، عمومی یا خصوصی بودن، سازنده و زمان‌های ساخت و ویرایش را نگه می‌دارد. حذف سازنده اتاق را حذف نمی‌کند؛ ارجاع <code>created_by</code> خالی می‌شود.</li>
  <li><code>Membership</code>: رابطهٔ کاربر و اتاق و نقش او (<code>member</code> یا <code>admin</code>) را ثبت می‌کند. برای هر جفت کاربر و اتاق فقط یک عضویت مجاز است.</li>
  <li><code>Message</code>: متن، اتاق، فرستنده، زمان ارسال و شناسهٔ اختیاری کلاینت را نگه می‌دارد. متن حداکثر ۴۰۰۰ نویسه است.</li>
</ul>

هر اتاق می‌تواند چند عضویت و پیام داشته باشد؛ هر کاربر هم می‌تواند عضو چند اتاق و فرستندهٔ چند پیام باشد. حذف اتاق، عضویت‌ها و پیام‌هایش را پاک می‌کند. حذف کاربر نیز عضویت‌ها و پیام‌های او را پاک می‌کند.

برای ساخت اتاق خصوصی باید دست‌کم یک کاربر دیگر را دعوت کنید. ادمین اتاق می‌تواند اعضای عادی را اضافه یا حذف کند؛ نقش ادمین از مسیر حذف عضو قابل حذف نیست.

قید یکتای شرطی روی <code>(room, sender, client_id)</code> از ثبت دوبارهٔ پیام هنگام retry جلوگیری می‌کند؛ این قید فقط وقتی اعمال می‌شود که <code>client_id</code> خالی نباشد. ایندکس‌های پیام هم خواندن تاریخچه بر اساس اتاق و شناسه/زمان را پشتیبانی می‌کنند. وضعیت آنلاین در PostgreSQL ذخیره نمی‌شود و فعلاً در حافظهٔ سرویس realtime است.

## چند نکته دربارهٔ پیاده‌سازی

<ol dir="rtl">
  <li>Django مرجع اصلی داده و هویت کاربر است. سرویس Node.js اتصال‌های WebSocket را مدیریت می‌کند.</li>
  <li>پیام قبل از پخش در PostgreSQL ذخیره می‌شود؛ در نتیجه کلاینت پیام تأییدنشده‌ای دریافت نمی‌کند.</li>
  <li>هویت فرستنده از توکن کاربر به دست می‌آید. سرور مقدار <code>sender</code> ارسالی از مرورگر را قبول نمی‌کند.</li>
  <li><code>client_id</code> و قید یکتای <code>(room, sender, client_id)</code> جلوی ذخیرهٔ دوبارهٔ یک پیام را می‌گیرند. رابط کاربری هم پیام‌ها را با <code>message.id</code> یکی می‌کند.</li>
  <li>تاریخچه با <code>before_id</code> صفحه‌بندی می‌شود تا هنگام رسیدن پیام‌های تازه، جای پیام‌های قدیمی در صفحه جابه‌جا نشود.</li>
  <li>وضعیت آنلاین در حافظهٔ یک نمونه از سرویس نگهداری می‌شود. اگر چند نمونه اجرا کنید، این وضعیت بین آن‌ها مشترک نخواهد بود؛ برای آن حالت باید از Redis استفاده شود.</li>
</ol>

جزئیات قرارداد درخواست‌ها و رویدادها در [قرارداد API](docs/API_CONTRACT.md) است. دلیل انتخاب‌های معماری و محدودیت‌هایشان را هم در [تصمیم‌های معماری](docs/DECISIONS.md) نوشته‌ایم.

## تنظیمات مهم

فهرست کامل تنظیمات در `.env.example` است. این‌ها مهم‌ترین مواردند:

| متغیر | پیش‌فرض | کاربرد |
|---|---|---|
| `DJANGO_SECRET_KEY` | — | کلید محرمانهٔ Django؛ برای هر محیط مقدار جداگانه بگذارید. |
| `INTERNAL_SERVICE_TOKEN` | — | احراز هویت درخواست‌های داخلی بین Django و realtime |
| `CORS_ALLOWED_ORIGINS` | — | مبدأهایی که اجازهٔ دسترسی به API دارند |
| `MAX_MESSAGE_LENGTH` | `4000` | حداکثر طول پیام |
| `RATE_LIMIT_WINDOW_MS` / `RATE_LIMIT_MAX_MESSAGES` | `10000` / `20` | بازه و تعداد مجاز پیام‌ها برای هر اتصال |
| `PRESENCE_TTL_MS` | `90000` | مهلت حضور پس از آخرین heartbeat |
| `PRESENCE_SWEEP_INTERVAL_MS` | `15000` | فاصلهٔ پاک‌سازی اتصال‌های منقضی‌شده |
| `HEARTBEAT_INTERVAL_MS` | `25000` | فاصلهٔ ارسال heartbeat |

`PRESENCE_TTL_MS` را بزرگ‌تر از `HEARTBEAT_INTERVAL_MS` نگه دارید؛ وگرنه ممکن است اتصال سالم پیش از heartbeat بعدی منقضی شود.

## سلامت و گزارش‌ها

<ul dir="rtl">
  <li><code>GET /healthz</code> سلامت سرویس را گزارش می‌کند. health check سرویس realtime دسترسی به Django را هم می‌سنجد و در صورت مشکل، پاسخ <code>503</code> می‌دهد.</li>
  <li><code>GET /readyz</code> وضعیت آماده‌به‌کار بودن را نشان می‌دهد و <code>GET /presence?room=&lt;slug&gt;</code> وضعیت آنلاین یک اتاق را برمی‌گرداند.</li>
  <li>گزارش‌ها به‌شکل JSON و یک‌خطی هستند و <code>request_id</code> دارند. متن پیام و توکن‌ها در گزارش ثبت نمی‌شوند؛ فقط طول متن پیام ثبت می‌شود.</li>
</ul>
